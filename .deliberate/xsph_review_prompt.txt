BUG: the XSPH viscosity kernel (src/solvers/xpbd/water.wgsl, fn xsph) accumulated
`dv += (vel[j]-vi) * w_poly6(r,h)` — an UNNORMALIZED kernel sum. w_poly6 ∝ 1/h^9, so Σ W_poly6 ∝
1/h^3, which grows as resolution refines (h = 2*spacing). At fine spacing a fixed xsph_c overshoots
(xsph_c * Σ W * Δv >> Δv), AMPLIFYING velocity instead of smoothing. xsph runs AFTER finalize's
max_speed clamp and rewrites vel, so it un-caps the velocity → catastrophic eruption at fine
resolution (vmax 10^5+, water sprayed everywhere). At the default spacing 1.0 the sum is tame so it
was never caught.

FIX: standard XSPH normalization — multiply the kernel term by the particle volume V_w = m/ρ0
(`dv += (vel[j]-vi) * (w_poly6(r,h) * v_w)`), so Σ V_w·W ≈ 1 (dimensionless, resolution-independent)
and xsph_c behaves consistently at any spacing.

1. Is this the correct standard XSPH normalization (m_j/ρ_j ≈ V_w for equal-mass water)? Any sign/
   factor error?
2. At the default spacing 1.0 it changes the effective viscosity by the V_w factor — is that a concern?
   (The full water/dam-break/wetting/coupling/geometry suites still pass unchanged.)
3. Does it correctly fix the resolution dependence, and is the post-clamp-amplification analysis right
